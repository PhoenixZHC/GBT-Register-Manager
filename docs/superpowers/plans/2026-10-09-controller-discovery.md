# 查找控制柜：开发方案与实施计划

最新结论（2026-10-12）：用户确认 v1.3.2 全功能测试通过，本轮功能验收完成，详见 [验收记录](../../acceptance-1.3.2-2026-10-12.md)。下文保留当时的检查结果和限制，不作为当前待修清单。

日期：2026-10-09。状态：本地代码已实现并完成下述本地验证，实机与安装验收待完成；当前 v1.3.0（基线 v1.2.8），未正式发布。

目标：用户忘记控制柜 IP，甚至不知道其 IP 网段时，可从连接页查找同一二层网络中的控制柜，查看 IP、MAC 并回填连接地址。

架构：Vue 展示搜索页面，Rust 管理独立扫描任务和进程，Python 实现现有二层发现协议。复用现有 Python Sidecar 可执行文件，扫描代码独立成模块，按需加载 Scapy，通过用户自行安装的 Npcap 收发报文。

技术栈：Vue 3、TypeScript、Naive UI、Tauri 2、Rust、Python、Scapy、Npcap。首期目标为 Windows x64。

需求依据：本次用户确认的要求，完整记录在下文。执行时遵守项目 AGENTS.md；本计划不授权安装系统驱动、创建分支、发布或操作机器人数据，不要求额外的逐节审批、提交或子代理派工。

## 1. 已确认的范围

- 首页连接区域增加“忘记控制柜 IP？点击查找”入口，进入独立搜索页面。
- 未连接机器人即可搜索，保留“不知道控制柜 IP 网段也能发现”的能力。
- 列表显示控制柜 IP 和 MAC；选择后回填控制柜 IP。
- 用 Python 重写原 Go 扫描逻辑，保持线上的请求与回复协议一致。
- **仅在进入查找控制柜页面时检测 Npcap**；用户点击重新检测或重新搜索时可再次检查。
- **不在安装、安装完成、首次启动或普通启动时检测 Npcap。**
- 工具箱不捆绑、不下载、不自动或静默安装 Npcap，也不自动启动驱动服务或修改其配置。
- 未安装时提示用户自行安装，提供官方下载入口、重新检测和返回连接。
- 缺少 Npcap 不影响手动输入 IP、寄存器和现有功能。
- TP 地址继续手动填写，选择控制柜时保留 TP 原值；不推断两者配对。

## 2. 能力边界

发现依赖二层以太网广播。电脑和控制柜需要二层互通，例如直连或同一交换机、同一 VLAN，且控制柜固件支持并响应该协议。不承诺跨路由、跨隔离 VLAN 或找到所有在线设备。

IP 不同网段也可能发现，但“发现”不等于 SDK 已可连接。选中后只回填 IP，不自动连接、不修改电脑或控制柜 IP、掩码和路由。必要时提示用户检查电脑与控制柜的网络配置。

当前源码的响应字段没有 TP 地址、设备型号、序列号或 TP 配对信息，页面不得编造这些字段。MAC 是设备识别线索，不构成身份认证；响应不能触发写入机器人或执行命令。

不增加 UDP 扫描、全网段穷举、远程改 IP、自动安装驱动或自研驱动。后续若需要，另行确定需求。

## 3. 页面与交互

连接页在 IP 输入区下方增加文字入口。搜索页保持现有视觉与五语体系，包含：返回连接、说明、网卡选择、搜索状态、结果表格、停止搜索／重新搜索。

进入页面后执行依赖检测：

| 检测结果 | 页面行为 |
|---|---|
| Npcap 可用且存在可用网卡 | 默认选择可用以太网接口并开始一轮搜索 |
| 未检测到 Npcap | 显示安装提示；提供官方下载、重新检测、返回连接 |
| 检测到安装信息但 DLL 无法加载或驱动不可用 | 显示组件不可用及具体诊断，不误报为未安装 |
| 无权限打开接口 | 显示权限不足，不自动提权或循环弹出权限请求 |
| 没有可用接口 | 提示检查网线、网卡启用状态及驱动 |
| 部分接口失败 | 保留其他接口发现结果，并明确标记搜索范围不完整 |

未安装提示：

> 未检测到 Npcap，查找控制柜功能需要此组件。请自行下载安装，安装后点击“重新检测”。手动输入 IP 连接不受影响。

官方下载按钮仅由用户点击后打开固定 HTTPS 地址 https://npcap.com/#download ，不接受报文或可编辑字段传入任意 URL。

结果列：控制柜 IP、MAC、发现它的本机网卡、操作“使用此 IP”。掩码和网关可保留在内部数据中，本期不增加网络配置编辑功能。

- 收到回复即增量显示，不等扫描完成；允许搜索期间选择已发现结果。
- 同一 MAC＋IP 去重，合并来源网卡；同一 MAC 返回不同 IP 时保留多条。
- 同一 IP 对应不同 MAC 时保留记录并提示地址冲突，不擅自选取。
- “使用此 IP”：先终止扫描并回收资源，再返回连接页、填入控制柜 IP，保留 TP 值；用户自行点击连接。
- 返回、重新搜索、窗口关闭均清理扫描任务；旧任务结果不得更新新页面。
- 空结果提示“本轮未发现控制柜”，并提供网线、网卡、二层隔离及协议支持检查方向，不宣称网络中没有控制柜。

## 4. 发现协议与实现约束

原始参考目录：`捷勃特机器人控制器IP&MAC扫描软件源码/controllers_serach/`。保留其源码作为参考，不直接修改或将其作为运行依赖。

| 项目 | 原协议 |
|---|---|
| 请求以太网类型 | `0xEEEA` |
| 请求目标 MAC | `FF:FF:FF:FF:FF:FF` |
| 请求源 MAC | 当前发送网卡的 MAC |
| JSON 字段 | `id`、`src`、`cmd`、`param` |
| 固定值 | `src="send_broadcast.go"`，`cmd="get_controller_ips"`，`param=""` |
| 请求 ID | 每轮独立的 8 位字母数字字符串；同一轮各网卡共用 |
| 回复以太网类型 | `0xEEEB` |
| 回复校验 | `id` 匹配，`dest="send_broadcast.go"`，`data.code=1000` |
| 结果字段 | `data.res.ip/mac/mask/gateway` |

即使改为 Python，也保留线上 `src` 固定字符串，不能因文件名变化自行替换。先启动抓包并确认监听就绪，再发送请求；过滤回复协议，限制报文大小、结果数量，严格解析并校验 IP／MAC。

对于 `ip` 中的多行内容，不能照搬原代码“只取最后一行”；以实机回复核实格式，逐项验证 IPv4 后保留有效地址。以太网填充仅允许按明确规则去除尾部填充，不能任意截取 JSON 来掩盖坏包。

网卡按稳定接口标识去重，检查启用状态、以太网链路类型和有效 MAC；不能沿用原代码 `Flags == 22/30` 的硬编码。不得仅因 IPv4 为 `169.254.*`、没有 IPv4 或描述含特定单词就直接排除本可用于二层通信的物理接口。Wi-Fi、虚拟接口的可用性按实际链路能力判断，不保证均可发现。

扫描时长暂定 10 秒，监听就绪后在 0、2、4 秒发送有限重试；这些是工程初值，不是已验证性能指标。实机对照后调整并记录依据。不保留原程序固定等待两分钟和回车退出行为。

收到同网段之外的合法回复不丢弃。异常网卡独立报错；坏包、重复包、无关请求 ID 不应终止正常扫描。禁止把发包或抓包失败包装成“搜索成功但没有设备”。

## 5. 接口与进程生命周期

下列开发接口已实现：

- `check_controller_discovery()`：按需检查依赖并枚举接口；返回状态、接口列表和结构化错误。
- `start_controller_discovery({ scanId, interfaceIds })`：使用前端已登记的本轮唯一 ID，启动一个扫描子进程，返回启动状态。
- `cancel_controller_discovery({ scanId })`：幂等取消指定任务；不得影响其他机器人操作进程。
- Tauri 事件 `controller-discovery-event`：`scanId`、`kind`（`device/warning/finished/error`）及对应负载；完成原因区分超时、取消、失败。
- 设备数据：`ip`、`mac`、`interfaceIds`，可选 `mask`、`gateway`；不添加未经证实的型号或 TP 字段。

前端先注册监听再启动任务，所有事件先校验 `scanId`。后端同一时刻只允许一轮扫描；检测、取消和重新扫描也需要处理并发与迟到响应。扫描不依赖机器人连接会话，不能复用要求先连接的 `sessionId` 校验。

Python 使用现有帧边界协议输出 JSON；日志走 stderr。`bridge.py` 增加检测与发现 action，扫描模块延迟导入，不因普通启动或寄存器调用加载 Scapy、探测 Npcap。

现有 Sidecar 是单请求 stdin、随后关闭的调用模式，不能假设存在持续双向控制通道。Rust 单独持有扫描进程句柄，以有限轮询实现 Python 的正常超时退出；取消时终止并等待该扫描进程、回收输出读取线程，禁止按进程名称批量结束进程。监听只运行在扫描子进程内部，不遗留后台扫描服务。

依赖检测须区分组件缺失、加载错误、权限不足和接口不可用；不能仅凭某个 DLL 文件存在就判定可用。检查及扫描均在后台执行，不能阻塞 UI；依赖缺失、取消及子进程崩溃需有有界返回时间。
