## 目标与依据

用户要求：先做到原版能够完成的控制柜搜索，再在此基础上优化；用户无需判断或选择网卡。依据为本次客户现场反馈及工作区 v1.3.2 与原 Go v0.2 源码对比。客户现场实际可执行文件的版本、哈希与源码对应关系仍需核验。

完成标准：在约定的同机、同线、同控制柜对照场景中，原版能够发现的有效控制柜地址，工具箱也能发现；无需选择网卡，重复搜索能使用新出现的接口。单元测试、构建及首次成功发现均不能单独代替这项验收。

架构：优先保留 Vue / Rust / Python Sidecar / Scapy 的现有链路，仅修改发现模块。以原版协议和可观察行为为基线；如证据证明 Scapy 路径无法兼容，再在发现模块内评估直接 PCAP 或原 Go 实现，不预先重写整个工具箱。

执行遵守用户 AGENTS.md：不新增分支、worktree、强制子代理或审批流程；本计划不授权发布、安装驱动或修改机器人数据。旧计划保留为历史记录，与本计划冲突时以本计划为准。

## 已确认差异与待验证原因

| 差异 | 当前证据 | 处理要求 |
|---|---|---|
| 首次全选，重搜只保留旧选择与新列表的交集 | `ControllerDiscovery.vue` 的 `prepare()` | 后端每轮重新枚举，移除旧选择对扫描范围的限制 |
| 原版主流程等待约 120 秒，当前收包 10 秒，0/2/4 秒发包 | 两版扫描循环 | 先恢复至少 120 秒完整收包机会，不能未经对照就缩短 |
| 原版直接显示回复 MAC，当前不合规 MAC 导致整条回复丢弃 | 两版响应解析 | 有效 IP 的展示不能被非关键 MAC 字段阻断 |
| 原版 PCAP 枚举后通过 IP 找 MAC，当前依赖 Scapy 合并信息 | 原版 util 与本地 Scapy 代码 | 对照枚举、MAC 和实际打开/发送结果；缺信息不能静默消失 |
| 当前检查固定 Npcap 路径、权限、服务状态 | `driver_status()` | 区分真实不可用与预检误判；不以检测提示代替实际能力对照 |

这些是可确认的实现差异，不是已经证实的现场唯一根因。现有 13 项发现单元测试通过，只证明已有模拟条件下的逻辑。

## 范围与行为约束

- 进入搜索页即自动搜索，保留停止、重新搜索、返回和使用 IP；移除网卡选择控件及相关必选提示。每次重新搜索刷新接口列表，包括刚插入、刚恢复及前次打开失败后恢复的网卡。
- 扫描所有可用于该协议的接口，不按默认路由只选一张，不因无 IPv4、链路本地地址或名称含 virtual 就直接排除。来源网卡可保留为结果说明或诊断信息，不能要求用户选择。
- 先建立监听再广播；首轮请求先按原版字段和紧凑 JSON 序列化对齐。有效收包窗口为 120 秒；发送时刻先采用 0、2、4 秒及此后每 10 秒一次至 114 秒，最多 14 轮。新增重发是待对照验证的优化，不能宣称原版本来持续重发。
- 结果实时显示，用户可提前停止或使用结果；不因已找到一个控制柜而停止监听。保留去重、多地址、部分接口失败隔离与取消清理。
- 保留 EtherType、请求 ID、dest、成功码、JSON 类型和大小等校验。缺失/异常 MAC 不再单独造成有效 IP 隐藏；显示“MAC 未提供/格式异常”，不能伪造 MAC。合法 MAC 使用 MAC+IP 去重；异常 MAC 使用 IP+来源接口去重，并标记身份信息不足，不能据此认定无 IP 冲突。
- IP 解析先与原版真实响应对照，包含单行、多行、尾部换行及原版可解析的地址形式；有效地址不能被无关字段丢弃。发现展示与 SDK 可连接性分开，原版可显示但当前连接入口不支持的地址必须说明，不静默丢弃或承诺可连接。
- 不改电脑或控制柜网络配置，不自动连接，保留 TP；不增加 UDP 扫描、全网段扫描和网络配置功能。
- 保留按需加载、手动连接不受驱动缺失影响、不捆绑/自动安装驱动、不自动提权或改服务配置的约束。如果原版成功依赖了当前禁止的服务启动等副作用，记录实际证据及具体冲突，在单独授权前不得宣称能力已对齐。

### 3. 对齐收发、解析与可诊断性
